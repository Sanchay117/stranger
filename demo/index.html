The details

  • The owner plants a canary. Kane signs in as your real first account and saves a random string like stranger-canary-e18167.
  • A second account looks for it. Kane signs in as someone else, saves its own control, and checks the control is there, so an empty page can't pass.
  • Any sight of the canary is a leak. On the page, or in what the server sends: Stranger replays the stranger's own data requests, then again with no login at all.
  • New canary every run. Old data can't fake a pass, and a fix has to really hold.
  • A Claude Code skill. Tells the agent to run Stranger after touching auth or data, and how to act on each verdict. stranger install-claude adds it and the hook.
  • A Stop hook. While armed, the agent can't call the work done until Stranger says CLEAN. On a leak it gets the brief back.
  • Fixes go to the database. The brief names the table and the policy. Filtering rows in the page is ruled out, because the data would still reach the browser.
  • It knows when to stop. Three tries, then it hands over to a person with the report.
  • Exit codes. 0 clean, 1 leak, 2 inconclusive, 3 setup error.
  • One JSON line with --json, for any agent or pipeline.
  • A history file. .stranger/history.jsonl keeps every verdict with its Kane run links.
  • Proof anyone can open. Each Kane run has a public page with every step and a replay.
  • Kane CLI. npm install -g @testmuai/kane-cli, then kane-cli login.
  • Two test accounts you own on your app, in .env. Test accounts only: Kane types these passwords into your app, and Stranger keeps its run folders out of git.
  • A small config. Your URL, what to plant, where to look. npx github:Sanchay117/stranger init writes one, or the box at the top does.
  • Any stack. Supabase gets SQL in the brief, Firebase gets rules, anything else gets a server-side check to add.
